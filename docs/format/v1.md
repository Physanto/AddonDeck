# The `.deck` format, version 1

This document is the source of truth for the `.deck` text format. The parser in `@addondeck/core`, the blocks, the Studio and the instructions for language models all follow it. When they disagree with this document, they are wrong.

Format version 1 is written with English keywords only. Other languages are added later as language packs (see [Language packs](#language-packs)).

## Overview

A deck is plain text. It starts with an optional header, followed by slides separated by `---`. Slides contain Markdown text and blocks: pieces of content that a plugin draws and animates step by step.

```
format: 1
title: How an online payment works
theme: ocean

section: Introduction

# How an online payment works
What happens in two seconds when you buy something

notes:
  Ask who bought something online this week.

---

## The journey of a payment

sequence id=payment:
  Customer -> Shop: I want to pay $50
  Shop -> Bank: Is there enough balance?
  Bank --> Shop: Yes
  Shop --> Customer: Payment done!
```

The format is designed to be forgiving. Mistakes never stop the parser: they produce [diagnostics](#diagnostics), and the deck is rendered as well as possible. Every setting has a default, so a deck without a header works.

## Text, lines and encoding

- A deck is UTF-8 text. A leading byte order mark is ignored.
- Line endings `\r\n` and `\r` are read as `\n`.
- Lines and columns in diagnostics start at 1. Columns count UTF-16 code units, as most editors do.
- Trailing spaces at the end of a line are ignored, except where they separate [step annotations](#step-annotations).

## Keyword normalization

Keywords are compared after normalization, so writing them with capitals or accents never matters. This applies to header keys, directive and block keywords, option keys, enumerated values (such as theme names and `on`/`off`) and [ids](#ids).

To normalize a word:

1. Decompose it (Unicode NFKD) and remove combining marks, so `é` becomes `e`.
2. Convert it to lowercase.
3. Replace `_` and spaces with `-`, and trim it.

So `Sequence`, `SEQUENCE` and `séquence` all mean `sequence`, and `line_of_time` and `Line of time` both read as `line-of-time`.

Normalization never changes text that is displayed: titles, Markdown and block bodies keep exactly what was written.

## Header

The header is a list of `key: value` lines at the very beginning of the deck. Every key is optional.

```
format: 1
title: Quarterly results
author: Ana Pérez
theme: ocean
motion: energetic
watermark: off
```

### Header keys

| Key          | Value                                                             | Default                                         |
| ------------ | ----------------------------------------------------------------- | ----------------------------------------------- |
| `format`     | Format version, a positive integer                                | `1`                                             |
| `title`      | Free text, used as the document title                             | The first level-1 heading of the deck, or empty |
| `author`     | Free text                                                         | Empty                                           |
| `language`   | Language of the content, as a language tag (`en`, `es`, `pt-BR`)  | `en`                                            |
| `theme`      | Name of an installed theme (`paper`, `ocean`, `chalkboard`)       | `paper`                                         |
| `motion`     | Motion personality: `smooth`, `energetic`, `elegant` or `minimal` | `smooth`                                        |
| `color`      | Main color: `#rgb`, `#rrggbb` or a CSS color name                 | From the theme                                  |
| `accent`     | Accent color, same syntax as `color`                              | From the theme                                  |
| `font`       | Name of an installed font family                                  | From the theme                                  |
| `background` | Name of a background from the catalog, or a color                 | From the theme                                  |
| `watermark`  | `on` or `off` (also `yes`/`no`, `true`/`false`)                   | `on`                                            |

When the system asks for reduced motion, the `minimal` personality is used whatever `motion` says.

Values are taken as written, after trimming. Enumerated values (`theme`, `motion`, `watermark`) are [normalized](#keyword-normalization). Names of themes, fonts and backgrounds are checked against what is installed when that information is available.

### Where the header ends

The header is made of the lines at the start of the deck, ignoring blank lines and [comments](#comments), that look like `word: value` where `word` is a header key. It ends at the first line that is not one, or at the first `---`. That line starts the first slide.

- A line whose key is close to a header key (at most two edits away, such as `titel:`) is still part of the header: it is ignored with warning `W301` and a suggestion. A key that is exactly a block or directive keyword is never taken as a close header key, so `table:` ends the header even though it is two edits away from `title`.
- A repeated key produces warning `W302`; the last value wins.
- An invalid value produces warning `W303` and the default is used.

Correct:

```
title: Team update
theme: chalkboard

# Team update
```

Incorrect, with the result:

```
titel: Team update        → W301, ignored: did you mean "title"?
theme: neon               → W303, unknown theme; "paper" is used
watermark: maybe          → W303, expected on or off; "on" is used
```

A first slide that starts with a line such as `title: ...` would be read as header. To start a slide with such a line, put `---` before it or write any other line first.

## Slides

Slides are separated by a line containing three or more dashes (`---`) and nothing else. The separator must not be indented.

```
# First slide

---

# Second slide
```

- A separator always ends the slide, even inside a Markdown code fence. To show `---` inside a slide, use a `code` block or indent it.
- A slide with no content (only blank lines, comments or directives) is skipped with information `I402`. Its directives still apply: a `section:` on an empty slide starts the section at the next slide.
- Blank lines before the first separator or after the last one are not a slide, and are skipped without `I402`. So a deck may start or end with `---`.
- `***` and `___` are not separators; they are Markdown horizontal rules.

## Slide directives

Directives are keywords that configure a slide. They are recognized only in the leading lines of a slide: the lines before its first text, block or notes, ignoring blank lines and comments. Elsewhere they are plain text, with warning `W306`.

### `section:`

`section: Name` starts a new section with this slide. The section continues until the next `section:`. Sections feed the agenda, the progress bar and section navigation. Slides before the first `section:` belong to no section.

A section always has at least one slide. When several `section:` directives come before the same slide, the last one wins; a `section:` after the last slide is dropped.

```
section: Results

## Sales by region
```

An empty name produces warning `W303` and the directive is ignored.

### `slide:`

`slide:` sets options for the current slide as `key=value` pairs.

```
slide: background=aurora transition=zoom layout=columns
```

| Option       | Values                                            | Default             |
| ------------ | ------------------------------------------------- | ------------------- |
| `background` | Name of a background from the catalog, or a color | The deck background |
| `transition` | `none`, `fade`, `slide` or `zoom`                 | `fade`              |
| `layout`     | `auto`, `columns` or `rows`                       | `auto`              |

With `layout=auto`, one block fills the slide, a heading plus one block stacks them, and two blocks sit side by side.

A slide's `transition` plays when the presentation moves to it from the previous slide, and in reverse when it moves back from it to the previous one. Jumping further, for example from the address bar, cuts. When the system asks for reduced motion, transitions take no time.

- Unknown option: warning `W308`, with a suggestion when one is close.
- Unknown value: warning `W309`, and the default is used.
- A word without `=`: warning `W314`, and the word is ignored.
- Several `slide:` lines are merged; for a repeated option the last value wins.

## Text

Every line that is not part of the header, a directive, a block, notes or a comment is text. Consecutive text lines form one text node, which the implicit `text` block renders as Markdown.

```
## Why trains

They are **faster** than buses between these cities, and you can work on board.

- Lisbon to Coimbra: 1 h 40 min    @1
- Coimbra to Porto: 1 h            @2

<b>This tag is shown as written, not as bold text.</b>
```

- Supported Markdown: headings, paragraphs, emphasis, strong text, links, inline code, lists, block quotes and fenced code.
- Raw HTML is never interpreted: it is shown as literal text.
- Blank lines inside text are kept (they separate paragraphs); blank lines at the start and the end of a text node are dropped.
- Text lines may end with [step annotations](#step-annotations). How the `text` block turns text into steps is part of that block's documentation.
- Inside a fenced code block (lines between ` ``` ` or `~~~` fences), lines are taken literally: they are never directives, blocks or comments. A fence that is not closed ends with its slide, with warning `W311`.
- A line that starts with `\` is always text. The backslash stays for Markdown, which renders `\#`, `\-` or `\/` as the literal character.

## Blocks

A block is a piece of content drawn by a plugin, such as a `sequence` diagram or a `table`. It starts with a header line and continues with an indented body.

```
sequence id=payment:
  Customer -> Shop: I want to pay
  Shop --> Customer: Done
```

### Block header

```
keyword [argument ...] [key=value ...]:
```

A line starts a block when **all** of these hold:

1. It is not indented.
2. Its first word, [normalized](#keyword-normalization), is the type or an alias of an installed block.
3. It ends with `:`, and nothing but arguments and options comes before that colon. Spaces before the colon are allowed.

The parts of the header:

- **Keyword:** the block type (`sequence`) or one of its aliases.
- **Arguments:** bare words, kept in order. Their meaning belongs to the block, such as the language in `code python:`.
- **Options:** `key=value` pairs. Keys are normalized; values are kept as written. A value with spaces goes in double quotes, where `\"` stands for a quote: `caption="Two words"`.
- **`id=`:** a reserved option that names the block, so [step annotations](#step-annotations) can refer to it.

Arguments and options may be mixed in any order. The block decides which arguments and options it accepts and reports its own diagnostics about them.

### Block body

The body is every following line that is indented or blank, up to the first non-blank line that is not indented. See [Indentation](#indentation). Blank lines inside the body are kept; blank lines at its end are dropped.

The body is passed to the block as written, line by line, with each line's number. Core does not interpret it: comments, annotations and arrows inside a body mean whatever the block says they mean. Blocks use the shared step annotation syntax so that it works the same everywhere.

A block may have an empty body when its arguments and options are enough:

```
image src=team.jpg alt="The team at the offsite":
```

### What is not a block

| Line                                | Result                                                                                   |
| ----------------------------------- | ---------------------------------------------------------------------------------------- |
| `Note: remember to smile`           | Text: `note` is not a block keyword.                                                     |
| `Sequence: the order matters`       | Text, with information `I403`: a block keyword followed by text after the colon is text. |
| `sequence id=pay` + indented lines  | Text, with warning `W305`: the header lacks its final colon.                             |
| `secuence id=pay:` + indented lines | Text, with warning `W304` and the suggestion `sequence`.                                 |
| `Steps:` + an indented list         | Text, silently: `steps` is not close to any keyword and has no options.                  |
| `  sequence:` (indented)            | Not a block header: it belongs to the text or body around it.                            |

An unknown block is only reported when its keyword is at most two edits away from a known keyword or when its header has options; otherwise text that happens to end in a colon would produce noise. Either way it is shown as text, never dropped. Suggestions consider block keywords and the keywords `notes`, `section` and `slide`, so `note:` followed by indented lines suggests `notes`.

A block whose plugin fails while reading its body or listing its steps (error `E201`) or cannot build anything from it is kept in its slide, with its id, and shown as text.

## Indentation

Block bodies and notes are indented with two spaces or one tab. For indentation purposes a tab counts as two spaces.

- The indentation of the first non-blank body line is the body's base indentation. That much leading whitespace is removed from every body line before the block reads it; deeper indentation is kept, so blocks can nest structure.
- A body line indented less than the base, but still indented, keeps its content and produces warning `W312`.
- Blocks receive both the line as written and the line without the base indentation.

```
code python id=client:
  lines:
    r = requests.post("/pay", amount=50)
```

Here the base indentation is two spaces; the block reads `lines:` and `  r = requests.post(...)`.

## Step annotations

Each slide has a list of steps: every click of the presenter advances one step. Blocks offer steps in order of appearance by default. Step annotations change that:

- `@n` at the end of a line assigns what that line does to step `n` of the slide. Steps are numbered from 1.
- `→ id` or `-> id` at the end of a line makes the block with that [id](#ids) advance in the same step.

```
code python id=client:
  lines:
    r = requests.post("/pay", amount=50)    @1 → network
    if r.status == 200:                       @2 → network
        print("Paid!")                        @3

sequence id=network:
  Client -> Server: POST /pay
  Server --> Client: 200 OK
```

The annotation is the end of the line, separated from the content by **two or more spaces or a tab**, and made only of an optional `@n` followed by any number of `→ id` or `-> id`. For example `@1`, `→ network`, `@2 → network → log`. The arrow may also touch its id (`→network`), and the id must be a valid [id](#ids); otherwise the arrow is content.

- When the end of a line can be read in more than one way, the longest annotation separated by two spaces is used: in `A -> B  -> C` the content is `A -> B` and the annotation is `-> C`.
- A line made only of `@n` with a single space before it, such as `print("x") @3`, keeps `@3` as text and produces warning `W307`, explaining that two spaces are needed.
- `@0`, a negative number or a non-number produces warning `W310`; the annotation is ignored and not shown.
- A `→ id` naming no block on the same slide is error `E204`. A `→ id` naming a block that offers no steps is valid and does nothing.
- Annotations are read in text lines and, through the shared helper, in block bodies. They are not read in the header, in directives or in notes.
- `@n` at the start of a line is not an annotation: some blocks use it for their own syntax.

Two spaces are required because arrows are content in some blocks: in `Customer -> Shop: Hello`, the arrow is a message, not an annotation.

## Step plan

Before a slide is shown, its annotations and the steps of its blocks are compiled into a **step plan**: for each click, which text and blocks advance. In the example above, click 1 highlights the first line and sends the request, click 2 highlights the second line and sends the answer, and click 3 prints the result.

What offers steps:

- Each block offers the steps its definition lists, usually one per line or item. A block shown as text offers none.
- A text offers one step per line with a step annotation. Text without annotations is shown from the start.

How steps are placed, reading the slide from top to bottom:

1. **Each block keeps its own order.** A block plays its steps one after the other, never out of order.
2. **Default order.** A step without `@n` takes the click after the last one used so far, so the steps of one block come before those of the next.
3. **`@n`** places a step in click `n`. Several steps, of the same block or of different ones, can share a click. A step pinned before an earlier step of its own block plays together with that earlier step, with warning `W315`.
4. **`→ id`.** The first arrow naming a block plays that block's first step in the same click, the second arrow its second step, and so on, in order of appearance. A step played by an arrow ignores its own `@n`. Arrows beyond the block's steps do nothing.
5. **Steps no arrow plays** follow rules 2 and 3, never before the steps the arrows played. A block written before the lines that point at it continues right after the last of them.
6. **Cycles.** Steps that wait for each other through arrows (`a` points at `b` and `b` points at `a`) take the default order at the end of the slide. A block pointing at itself plays in the default order.
7. **No empty clicks.** Clicks in which nothing would change are removed: a slide with only `@1` and `@5` has two clicks.

```
sequence id=network:
  Client -> Server: POST /pay
  Server --> Client: 200 OK
  Client -> Client: show receipt

- Pay       @1 → network
- Confirm   @2 → network
- Done      @3
```

Here the third message of `network` is not played by any arrow, so it continues right after `Confirm` and shares click 3 with `Done`.

## Speaker notes

`notes:` on a line of its own starts speaker notes for the current slide. The notes are the indented lines that follow, with the same rules as a [block body](#block-body). They are shown only in presenter mode.

```
# Welcome

notes:
  Thank the organizers.
  Mention the survey at the end.
```

- `notes:` may appear anywhere in the slide. Several notes in one slide are joined, separated by a blank line.
- `Notes: buy milk`, with text after the colon, is ordinary text with information `I403`, like a block keyword followed by text. The remark matters because the line is shown on the slide, not in the notes.
- `notes:` without indented lines below produces warning `W313`.

## Comments

A line that starts with `//`, without indentation, is a comment and is ignored.

```
// TODO: replace the chart with real numbers
## Results
```

Inside block bodies, notes and fenced code, `//` is content: in a `code` block it may well be part of the code.

## Ids

An id names a block: `id=payment`.

- It starts with a letter and contains only letters, digits, `-` and `_`. Otherwise it is error `E203`.
- Ids are [normalized](#keyword-normalization) before comparing, so `id=Payment` and `→ payment` match.
- Ids are unique in the whole deck. A repeated id is error `E202`.

## Diagnostics

The parser and the step plan never fail. Every problem becomes a diagnostic with a stable code, a position, a message and, when possible, a suggestion. Diagnostics are listed in order of position.

| Severity    | Codes                           | Meaning                                                        |
| ----------- | ------------------------------- | -------------------------------------------------------------- |
| Error       | `E1xx` structure, `E2xx` blocks | The deck can be previewed, but not exported until it is fixed. |
| Warning     | `W3xx`                          | Something was ignored or replaced by a default.                |
| Information | `I4xx`                          | Worth knowing; nothing was lost.                               |

Messages are written in English and come from a translatable text catalog; codes never change meaning, so tools and language models can learn to fix them. Blocks report their own diagnostics with codes of their own.

| Code   | Meaning                                                                                 |
| ------ | --------------------------------------------------------------------------------------- |
| `E101` | The `format` version is newer than this parser supports. The deck is read as version 1. |
| `E102` | The `format` value is not a positive integer.                                           |
| `E201` | A block failed while reading its body or listing its steps. It is shown as text.        |
| `E202` | An id is used more than once.                                                           |
| `E203` | An id has characters that are not allowed.                                              |
| `E204` | A `→ id` names no block on the slide.                                                   |
| `W301` | Unknown header key, ignored.                                                            |
| `W302` | Repeated header key; the last value wins.                                               |
| `W303` | Invalid value for a header key or directive; the default is used.                       |
| `W304` | Unknown block keyword; the block is shown as text.                                      |
| `W305` | A block header without its final `:`; shown as text.                                    |
| `W306` | A slide directive after the start of the slide; shown as text.                          |
| `W307` | A step annotation separated by a single space; shown as text.                           |
| `W308` | Unknown slide option, ignored.                                                          |
| `W309` | Invalid value for a slide option; the default is used.                                  |
| `W310` | Invalid step number, ignored.                                                           |
| `W311` | A code fence that is never closed; it ends with its slide.                              |
| `W312` | A body line indented less than the rest of its block.                                   |
| `W313` | `notes:` with no indented text below it.                                                |
| `W314` | A word without `=` in slide options, ignored.                                           |
| `W315` | A step pinned before an earlier step of its own block; it plays with that step.         |
| `I401` | No `format` key; version 1 is assumed.                                                  |
| `I402` | An empty slide was skipped.                                                             |
| `I403` | A block keyword or `notes` followed by text after the colon; the line is text.          |

## Language packs

Version 1 ships with English keywords only. A language pack is a data file that adds aliases in another language without changing the parser or any block. A pack can provide:

- aliases for header keys, directive keywords (`section`, `slide`, `notes`), option keys and enumerated values (theme and motion names, `on`/`off`);
- aliases for block types and for words that blocks define;
- translated diagnostic messages and interface texts.

Rules:

- Aliases are [normalized](#keyword-normalization) like keywords.
- English keywords are always accepted. A deck may mix languages, and every installed pack is active whatever the `language` key says; `language` describes the content, not the keywords.
- An alias may not clash with a keyword or alias of a different meaning; such a pack is rejected when it is installed.
- Messages missing from a pack fall back to English.

For example, a Spanish pack could map `secuencia` to `sequence`, `titulo` to `title` and `si` to `on`, so that `titulo: Mi charla` and `title: Mi charla` mean the same.

## Versioning

- `format: 1` declares this version. Without it, version 1 is assumed (information `I401`).
- Incompatible changes only happen in a new major version of the format, and the parser ships migrations to read earlier versions.
- New keywords, options and values may be added within version 1, because unknown ones are already reported as warnings rather than errors.

## Resolved ambiguities

Decisions taken where a line could mean two things. Each one is also described in its section.

1. **Keyword followed by text is text.** A line starts a block, notes or a slide directive with options only as described above; `Note: something`, `Notes: buy milk` and `Sequence: the order matters` are text.
2. **Unknown blocks are reported only when they look like blocks.** The keyword must be close to a known one or the header must have options; otherwise an indented list after a label such as `Steps:` would be flagged.
3. **Close header keys keep the header going.** `titel:` in the header is ignored with a suggestion instead of ending the header and turning the following settings into slide text.
4. **Directives only at the start of a slide.** `section:` or `slide:` further down a slide is text, with a warning.
5. **Separators always separate.** `---` ends a slide even inside a Markdown code fence, so an unclosed fence can never swallow the rest of the deck.
6. **Annotations need two spaces.** Arrows are content in some blocks, so `@n` and `→ id` only count at the end of a line after two or more spaces or a tab. A lone `@n` after a single space is reported, not guessed.
7. **Comments only without indentation.** Indented `//` lines belong to block bodies and notes, where they may be code.
8. **Annotations at the start of a line belong to blocks.** `@1 r = waiting` inside a body is block syntax, not a core annotation.
9. **`language` does not choose keywords.** All installed language packs are always active, so a deck written with mixed keywords still works.
10. **Raw HTML is shown, not run.** Deck text is never executed outside an explicit `custom` block.
11. **Arrows pair with steps in order.** The k-th `→ id` naming a block plays that block's k-th step, so a block keeps its own order whatever the clicks of the lines that point at it.
12. **Gaps in `@n` do not make empty clicks.** `@1` and `@5` alone are two clicks; the numbers only order the steps.
